# Маркетинговая фабрика mi-code.pl

Повторяемое производство рекламных креативов для B2B-лидов mi-code.pl:
LinkedIn-карусели, одиночные посты, фид 4:5, Reels/Stories 9:16 и OG-карточки.
Полная стратегия — в `docs/superpowers/specs/2026-07-31-marketing-factory-design.md`.

Один campaign.json описывает кампанию один раз, генераторы рендерят его в
любой холст — так же, как `products.json` на самом сайте управляет страницами
продуктов вместо захардкоженной разметки.

## Структура

```
docs/marketing/
├── README.md              как всё устроено + команды регенерации
├── strategy.md            аудитория, каналы, воронка, метрики
├── content-plan.md        календарь: что / где / когда публикуем
├── campaigns/
│   └── <id>/campaign.json источник правды по кампании
├── copy/
│   ├── funnel-<id>.md     × 5  тексты верха воронки (PL/EN)
│   ├── product-<id>.md    × 6  тексты «продукт как доказательство»
│   └── cta-blocks.md      общая часть + блок CTA на каждую кампанию
├── creatives/<id>/
│   ├── src/               исходные скриншоты сайта
│   └── renders/{pl,en}/   carousel-01..N + carousel.pdf, li-single,
│                          feed-4x5, story-9x16, reel.mp4/gif, og.png
├── assets/
│   ├── micode-badge.png   копия из репо приложения
│   └── fonts/             Poppins + Open Sans (.ttf)
└── scripts/
    ├── fetch_fonts.py
    ├── spec.py             загрузка и валидация campaign.json, UTM-ссылки
    ├── brand.py            палитра, шрифты, бейдж, подвал
    ├── slides.py           рендер одного слайда на один холст
    ├── render_warnings.py  общий релей предупреждений рендера в stderr
    ├── build_carousel.py
    ├── build_single.py
    ├── build_reel.py
    └── capture_screens.py
```

На момент этого коммита реализованы весь `scripts/` (`spec.py`, `brand.py`,
`fetch_fonts.py`, `capture_screens.py` и все три генератора —
`build_carousel.py`, `build_single.py`, `build_reel.py`), `assets/fonts/`,
`assets/micode-badge.png` и полный набор тестов под `tests/`, а также
`strategy.md`, `content-plan.md` и две настоящие кампании верха воронки:

- `cost-of-ai-agent` — 6 слайдов, включая слайд `diagram` со снимком
  калькулятора из статьи;
- `rag-without-hallucinations` — 6 слайдов, **без** слайда `diagram`
  (обоснование — в `strategy.md`), поэтому `capture_screens.py` ей не нужен.

У каждой — `campaigns/<id>/campaign.json`, тексты `copy/funnel-<id>.md`, блок
в `copy/cta-blocks.md` и все пять форматов в
`creatives/<id>/renders/{pl,en}/`. Остальные 9 кампаний из `strategy.md` —
следующая фаза; кода она не требует, только `campaign.json` и файл в `copy/`.

Рендеры лежат в git намеренно. Во-первых, `tests/test_campaigns.py`
проверяет, что они существуют и имеют нужный размер, — иначе набор тестов
краснеет на чистом клоне. Во-вторых, это и есть тот файл, который оператор
загружает в LinkedIn: пересобрать его можно только подняв `npm run build &&
npm run preview` и headless-браузер, а фабрика существует ровно для того,
чтобы этого не требовалось перед каждой публикацией. Цена — около 11 МБ на
кампанию (из них ~2,7 МБ — `reel.mp4` + `reel.gif`); на 11 кампаний это
~120 МБ, и к этому решению стоит вернуться до того, как приземлятся
оставшиеся девять.

## Тесты кампаний: один параметризованный свод

`tests/test_campaigns.py` параметризован по `campaigns/*/campaign.json` —
новая кампания попадает под все проверки в тот момент, когда появляется её
спека, без единой строчки нового кода. Проверяются: форма спеки, размер
колоды, наличие заголовков на обоих языках, все числа против собственной
статьи кампании, глифы против зашитых шрифтов, разделы и ссылки в
`copy/funnel-<id>.md` (сверяются с тем, что вернул бы `spec.Campaign.link`),
блок в `cta-blocks.md`, строка в `content-plan.md` и **весь** комплект
рендеров: `carousel-01..N` по числу слайдов, `story-9x16-01..N`,
`li-single`/`feed-4x5`/`og`, `carousel.pdf` и `reel.mp4`/`reel.gif`.

Две вещи, которые кампания объявляет о себе сама, в `campaign.json`:

```json
"source": {
  "slug": "legalka-kb-ai-architecture",
  "figures": ["109", "99", "97", "100", "28 091", "28,091"]
}
```

`slug` — статья, против тела которой сверяются все числа колоды (для верха
воронки поле обязательно); `figures` — опорные цифры, проверяемые в обе
стороны: и что они всё ещё в статье, и что они всё ещё на слайдах. Числа
пишутся в том виде, в каком стоят в статье, — польское `28 091` и английское
`28,091` это две разные записи и обе перечисляются.

В `tests/test_campaign_<id>.py` остаётся только то, что действительно про
одну колоду: у `cost-of-ai-agent` — что снимок калькулятора сделан в
референсной конфигурации статьи, у `rag-without-hallucinations` — что в
колоде нет слайда `diagram` и почему.

## Установка

Все Python-скрипты фабрики и её тесты используют один и тот же набор
зависимостей, зафиксированный в `docs/marketing/requirements.txt`:

```bash
pip install -r docs/marketing/requirements.txt
python -m playwright install chromium
```

Второй шаг обязателен отдельно: `pip install playwright` ставит только
Python-библиотеку, но не сам браузер — без `playwright install chromium`
`capture_screens.py` упадёт уже при попытке запустить браузер.

`imageio-ffmpeg` и `av` пиновать нужно оба, но не по одной и той же причине:
`build_reel.py` пишет `reel.mp4`/`reel.gif` через `imageio-ffmpeg` (это его
реальный продакшен-бэкенд для записи), а `av` нужен только тестам —
`tests/test_build_reel.py` читает записанное видео обратно через
`iio.imread(mp4, plugin="pyav")`, чтобы проверить содержимое кадров. Если
отсутствует `imageio-ffmpeg` (или оба пакета сразу), это не падает с понятным
"нет видеобэкенда" — `imageio.mimwrite` либо бросает `TypeError` про
неподходящий плагин, либо (если нет ни `imageio-ffmpeg`, ни `av`) падает с
непрозрачной ошибкой из `TiffWriter`, никак не намекающей, что дело в
отсутствующем видеобэкенде. Держите в голове эту ошибку, если она всплывёт —
решение не в том, чтобы поставить `imageio[pyav]` вместо `imageio-ffmpeg`;
он покрывает только путь для тестового чтения, а не запись, которую делает
`build_reel.py`.

## Скриншоты (`capture_screens.py`)

Диаграммы LangGraph на страницах продуктов рисует mermaid прямо в браузере —
никакого статического файла для копирования не существует, поэтому съёмка
экрана headless-браузером — единственный способ получить исходник для
`diagram`-слайдов.

Перед запуском нужно поднять собранный сайт локально (не dev-сервер — сборку,
как её увидит реальный посетитель):

```bash
npm run build && npm run preview
python docs/marketing/scripts/capture_screens.py cost-of-ai-agent
```

Съёмка нужна не всем кампаниям — только тем, у которых хотя бы один слайд
типа `diagram` объявляет в `campaign.json` блок `shot` (`path` и опциональный
`selector`). `capture_screens.py` берёт такие слайды через
`shots_for(campaign)`, открывает `{base_url}{path}` для каждого, при наличии
`selector` дожидается элемента через `page.wait_for_selector` и сохраняет
скриншот элемента — либо всей страницы, если `selector` не задан.

Файл кладётся ровно туда, куда его потом будет искать рендерер: путь считает
`capture_screens.target_for()`, а он вызывает тот же `spec.Campaign.asset()`,
которым `slides._place_diagram_frame` читает картинку обратно. То есть
`creatives/<id>/` + **весь** относительный путь из `asset`, а не только имя
файла: `"asset": "src/calc-pl.png"` → `creatives/<id>/src/calc-pl.png`. Раньше
это были две разные формулы (запись — всегда в `src/` по `Path(asset).name`,
чтение — по полному пути), и `"asset": "screens/x.png"` снимался в одно место,
а искался в другом: съёмка рапортовала успех, а слайд `diagram` рендерился без
диаграммы. Сейчас формула одна; и если файла всё-таки нет, `slides.py`
предупреждает и называет путь, по которому смотрел, — молча слайд больше не
деградирует.

`asset` — это имя файла, поэтому оно должно быть уникальным: если два языковых
блока назовут **один и тот же** `asset` с разными `path`, `shots_for` падает с
`SpecError`. Иначе вторая съёмка молча перезаписала бы первую и один из языков
уехал бы в ленту с чужим скриншотом.

Кампания без единого `diagram`-слайда с `shot` не требует запуска этого
скрипта вовсе.

### Селектор для mermaid-диаграмм: ждать SVG, а не элемент

Формулировка «берите селектор, а не фиксированную паузу — и тогда всё
дождётся» неверна, и пример `.calc-table-wrap` её не подтверждает: таблица
калькулятора приезжает готовой в предрендеренном HTML, ей нечего ждать, с ней
сработал бы и `wait_for_selector`, и пауза в ноль секунд.

С mermaid всё иначе, и это гонка. `MermaidDiagram.svelte` отдаёт в разметке
`<button class="diagram-wrap"><pre class="mermaid">{definition}</pre></button>`
с **исходным текстом** диаграммы внутри, а рисует её `mermaid.run()` в
`onMount` уже после динамического импорта пакета. Значит:

- `wait_for_selector('.mermaid')` и `wait_for_selector('.diagram-wrap')`
  возвращаются мгновенно — оба элемента есть в HTML с самого начала;
- `data-processed` mermaid ставит **до** отрисовки, так что он тоже не гарантия;
- `wait_until="networkidle"` на обычной машине успевает — измерено: без
  троттлинга SVG к этому моменту уже есть. При CPU-троттлинге 6× (то есть на
  рядовом CI-раннере) в DOM всё ещё лежит исходный текст, и съёмка
  сфотографировала бы его.

Ждать нужно сам результат:

```json
"shot": { "path": "/products/accounting-ai/",
          "selector": ".diagram-wrap:has(pre.mermaid svg)" }
```

`:has()` поддерживается движком селекторов Playwright, и это единственный из
перечисленных вариантов, который становится истинным только после того, как
mermaid действительно построил SVG.

`asset` и `shot` можно объявить **внутри языкового блока** `pl`/`en` слайда —
приоритет тот же, что у `rows`: язык перебивает уровень слайда, уровень слайда
остаётся фолбэком (по каждому ключу отдельно). Это нужно, когда снимаемая
страница рисует собственный текст: таблица калькулятора в статье берёт
заголовки и подписи строк из словарей `src/data/{pl,en}.json`, поэтому один
общий скриншот положил бы польскую таблицу на английский слайд. Пример —
слайд `diagram` в `campaigns/cost-of-ai-agent/campaign.json`: `pl` снимает
`/blog/…`, `en` — `/en/blog/…`, в два разных файла. Одинаковые по итогу
съёмки схлопываются, так что языконезависимая диаграмма (mermaid-граф) по-
прежнему стоит ровно одного захода браузера и одного файла.

Состояние страницы задаётся query-строкой прямо в `shot.path`: у калькулятора
`src/services/costEstimateUrl.ts` восстанавливает все ~12 полей из URL
(ключи camelCase: `stepsMin`, `stepsMax`, `cachedSharePct`, `model`,
`euResidency`, …). Без этого снимок показал бы дефолт компонента, а не
конфигурацию, о которой говорит статья.

## Регенерация

Полный пайплайн для одной кампании:

```bash
npm run build && npm run preview            # нужен только если у кампании есть слайд diagram
python docs/marketing/scripts/capture_screens.py cost-of-ai-agent
python docs/marketing/scripts/build_carousel.py cost-of-ai-agent pl en
python docs/marketing/scripts/build_single.py   cost-of-ai-agent pl en
python docs/marketing/scripts/build_reel.py     cost-of-ai-agent pl en
```

`pl en` во **всех трёх** генераторах, включая `build_reel.py`: закоммичены —
и `tests/test_campaigns.py` проверяет — английские `story-9x16-01..NN.png`,
`reel.mp4` и `reel.gif` тоже. Запуск с одним `pl` собрал бы только польские и
оставил английские постеры протухшими; ровно эта команда раньше и стояла в
этом файле. Без аргументов языка все три генератора теперь одинаково берут
`pl en` по умолчанию, а неизвестный язык (`ru`) отвергается сразу, до записи
первого файла, с внятным сообщением вместо `KeyError`.

Раньше это утверждение README было неправдой: тест смотрел только на
`story-9x16-01.png` и вообще не упоминал `reel.mp4`, так что забытый `en`
проходил зелёным. Теперь набор файлов сверяется с числом слайдов колоды, и
лишний постер от удалённого слайда падает так же, как недостающий.

Шрифты и бейдж регенерировать не нужно — они закоммичены (см. ниже) и
скачиваются один раз через `python docs/marketing/scripts/fetch_fonts.py`.

## Про `og.png`

`renders/<lang>/og.png` (1200×630) фабрика генерирует, но **сейчас его никто
не потребляет**, и это стоит знать до того, как кто-то пойдёт искать, где он
подключается.

У сайта есть собственный конвейер OG-карточек: `scripts/generate-og-images.mjs`
рисует `public/og/<slug>-<lang>.png` на каждую статью и каждую локаль, и
именно он подставляется в `og:image` через мета-теги страниц. Карточка фабрики
— это второе изображение 1200×630 для той же статьи, нарисованное в другой
системе (слайд `hook` кампании, а не заголовок статьи), и в разметку сайта
она не попадает.

Не удаляется намеренно, по двум причинам. Первая: 1200×630 — это стандартный
OG-размер для **ссылки, которую публикуют вручную** там, где превью тянется
не с сайта, и куда картинку прикладывают файлом. Вторая: она бесплатна —
`build_single.py` рендерит тот же слайд `hook`, что и `li-single`, третий
холст стоит доли секунды и ~150 КБ. Если вторая фаза так и не найдёт ей
применения, правильный шаг — убрать `og` из `build_single.CANVASES` вместе с
его строкой в `SINGLE_FORMATS` (`tests/test_campaigns.py`) и в
`test_build_single.py:58`, а не оставлять формат, про который
никто не помнит, зачем он.

## Шрифты коммитятся намеренно

`assets/fonts/` **намеренно** лежит в git, а не игнорируется и не качается на
каждом запуске сборки. Сайт подтягивает Poppins и Open Sans с CDN Google
Fonts в рантайме — креативам это не подходит: рендер должен быть одинаковым
и на машине разработчика, и на CI-раннере (обычно Linux) без сети. Скрипты
также никогда не должны обращаться к `C:/Windows/Fonts` или любому другому
системному пути — такого пути нет ни на Linux, ни в CI.

Файлы шрифтов и лицензии OFL лежат рядом в `assets/fonts/`:

- `Poppins-Bold.ttf`, `Poppins-SemiBold.ttf` — заголовки (`--font-heading` на
  сайте)
- `OpenSans-Regular.ttf`, `OpenSans-SemiBold.ttf` — текст (`--font-body` на
  сайте)
- `Poppins-OFL.txt`, `OpenSans-OFL.txt` — лицензии SIL Open Font License,
  допускающие распространение шрифтов вместе с репозиторием

Open Sans в `google/fonts` не публикуется статическими начертаниями
(`ofl/opensans/static/` отсутствует) — только вариативным файлом
`OpenSans[wdth,wght].ttf`. `fetch_fonts.py` скачивает вариативный шрифт и
через `fontTools` фиксирует нужные инстансы (`Regular`, `SemiBold`) в
отдельные статические `.ttf`, пригодные для `PIL.ImageFont.truetype`.

Чтобы перекачать шрифты заново (например, после апдейта апстрима):

```bash
python docs/marketing/scripts/fetch_fonts.py
```
